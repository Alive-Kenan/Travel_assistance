# 2026-05-30 景点兜底补全设计

## 背景

当前视频分析链路已经能够完成：

- 浏览器本地抽帧
- 第一阶段视频内容识别
- 第二阶段通过 Kimi 联网补全

但在真实使用中，仍存在一个关键体验问题：

- 视频分析完成后，页面可能没有展示出任何有效的景点内容
- 即使第一阶段已完成，返回的线索也可能过弱，只得到零散字段
- 即使第二阶段联网成功或部分成功，最终页面仍可能缺少景区名称、亮点和周边特色

这会让用户感知为“分析完成但没有结果”，与产品目标相冲突。

## 目标

- 视频分析完成后，页面必须尽量展示出与景点相关的有效内容
- 即使第一阶段识别较弱，也要尽可能补出：
  - 景区名称
  - 景点亮点
  - 周边特色或周边推荐
- 允许系统基于视频中的弱线索推断最可能景区，并继续联网补全
- 避免再次出现“分析完成后页面没有任何景点内容”或整体白屏

## 非目标

- 不追求百分之百准确识别景区
- 不引入服务端数据库或离线知识库
- 不替换现有 Kimi 抽帧分析主链路
- 不重做整套页面布局，仅修正数据契约和降级策略

## 核心思路

将“视频分析完成”从单纯表示“第一阶段跑完”提升为“页面已经拿到可展示的景点内容”。

为此，在现有两阶段链路后追加一套“结果充分性判断 + 两级兜底补全”策略：

1. 第一阶段完成后，先判断当前提取结果是否足够支撑页面展示
2. 如果结果不足，则先基于已提取线索发起一次联网补全
3. 如果联网补全后仍无法得到明确景区名称，则允许模型根据弱线索推断最可能景区
4. 基于候选景区再次补全景点信息
5. 最终页面至少展示一个景区名称或候选景区名称，以及部分亮点/周边特色

## 结果充分性判断

新增“结果是否足够展示”的判断规则。满足以下任一情况，视为信息不足，需要兜底补全：

- 没有景区名称
- 没有景点摘要
- `highlights`、`checkpoints`、`foodAndSouvenirs`、`nearbyRecommendations` 全部为空

满足以下条件之一，则视为可以正常展示：

- 有明确景区名称，且至少有一类景点内容非空
- 没有明确景区名称，但有足够多的线索可用于推断和联网补全

## 两级兜底补全策略

### 第一层：线索直补

当第一阶段结果不足时，先直接使用当前提取结果进行联网补全：

- 将第一阶段已有的文本线索、地名片段、亮点关键词、周边候选、饮食关键词等整理为搜索输入
- 调用 Kimi 的 `$web_search`
- 目标是尽量直接产出合法的 `SpotGuide`

适合以下场景：

- 已提取到部分地名或景观关键词
- 已提取到亮点、路线点、食物等可检索线索

### 第二层：候选景区推断后补全

如果线索直补后仍然没有明确景区名称，则进行候选景区推断：

- 让模型基于视频已提取到的弱线索，生成一个“最可能景区名称”
- 同时给出简短推断依据
- 基于这个候选景区名称，再次发起联网补全

此层允许“合理推断”，以满足用户“分析完成后必须有景点内容”的目标。

## 展示策略

### 明确识别结果

当模型已明确识别出景区名称且内容较完整时：

- 按完整结果展示
- 不增加额外提示

### 基于线索补全的结果

当景区信息来自第一阶段弱线索 + 联网补全时：

- 正常展示结果
- 增加轻提示：内容根据视频线索和联网信息整理

### 基于候选景区推断的结果

当景区名称来自模型推断而非明确识别时：

- 主卡仍展示候选景区名称
- 页面增加提示：该景区名称根据视频线索推断，建议进一步核验
- 其余亮点、周边信息照常展示

### 最终兜底

只有在以下情况同时成立时，才允许退回“提取版结果”：

- 无法明确景区名称
- 线索直补失败
- 候选景区推断后补全仍失败

即便如此，也必须尽量保留已有的部分景点线索，不允许出现全空内容页。

## 数据结构设计

为支持“推断景区”和“补全来源说明”，扩展 `SpotGuide` 或其展示上下文，增加以下元信息：

- `displayMode`
  - `full`
  - `partial`
  - `inferred`
- `displayHints`
  - 可选的提示文案数组

这类元信息不直接依赖 Kimi 返回，而由前端在组装结果时生成。

## 组件设计

### `useRideGuideStore`

增加三个阶段性动作：

- 判断第一阶段结果是否充分
- 不充分时执行线索直补
- 仍不充分时执行候选景区推断 + 二次补全

### `kimiClient`

新增两个方向的能力：

- 基于线索的补全调用
- 基于弱线索的候选景区推断调用

现有 `enrichSpotWithKimi()` 继续保留，但需要支持：

- 普通补全
- 候选景区驱动的补全
- 返回结果归一化

### `ResultPanel` / `SpotGuideCards`

根据结果模式显示不同提示：

- `full`：不提示
- `partial`：提示为视频提取版结果
- `inferred`：提示景区名称为推断结果，建议核验

## 错误处理

### 联网补全失败

- 继续透传真实错误
- 但不应立即停止
- 应根据阶段自动尝试下一层补救

### 候选景区推断失败

- 若前面已有部分景点线索，则保留已有结果展示
- 若无任何有效内容，则才进入 `error`

### 结果归一化

- 所有模型输出在进入组件前都必须先做合法化处理
- 不允许将原始模型 JSON 直接传给 UI

## 成功标准

- 视频分析完成后，页面至少展示一个与景点相关的主卡结果
- 没有再次出现“分析完成但没有任何景点内容”
- 第二阶段返回稀疏 JSON 时，仍能被归一化为可展示结果
- 当结果来自候选景区推断时，页面有明确提示
- 所有新增逻辑有自动化测试覆盖

## 风险与取舍

- 允许推断景区会引入误判风险，但这是用户明确接受的取舍
- 推断结果必须以提示文案标注，不应伪装成确定识别
- 多一次候选景区推断和补全会增加延迟，但比展示空结果更符合产品目标

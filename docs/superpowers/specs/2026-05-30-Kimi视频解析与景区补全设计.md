# Kimi 视频解析与景区补全设计文档

## 1. 背景与目标
当前项目已经完成“景点速查页”的前端界面与本地 mock 解析能力，但结果仍然依赖示例文本，而不是真实视频内容。当前新增目标是在 demo 场景下接入 Kimi API，让项目内置的本地测试视频成为真实输入，并通过两阶段模型调用生成最终景点速查卡。

本次设计聚焦于 demo 测试链路，而不是正式产品上传能力，因此需要明确以下前提：
- 当前不是给最终用户上传视频
- 当前视频是项目目录中的测试输入
- 页面上保留“替换视频”能力，仅用于开发调试
- API 调用采用前端直连 Kimi 的方式，不做后端代理
- 为了便于维护，请求体通过 JSON 模板文件组织

本次设计目标是：
- 让页面默认使用项目内置测试视频发起分析
- 用 Kimi 完成“视频理解 -> 景区补全”两阶段处理
- 将最终结果继续落到现有 `SpotGuide` 结构，复用当前前端页面
- 为视频过大、联网补全失败、模型 JSON 返回异常等情况提供可降级行为

## 2. 现状约束
- 项目当前为纯前端 React + TypeScript + Zustand 架构
- 当前结果页已经使用 `SpotGuide` 作为统一渲染结构
- 当前没有真实后端 API 层
- 当前没有专用 Kimi 配置文件

## 3. 方案结论
采用“前端直连 Kimi + 两阶段 JSON 模板驱动”的 demo 方案。

整体策略：
- 主体实现方式接近“整段视频直接送 Kimi”
- 但实现偏向“整段视频直传前先做文件大小和可用性检查”，以减少浏览器卡顿和失败率
- 第一阶段只做视频内容提取
- 第二阶段基于第一阶段结果调用 Kimi 内置 `$web_search` 补充景区信息
- 若第二阶段失败，页面仍展示第一阶段的基础结构化结果

该方案适合当前 demo 阶段，原因是：
- 改动范围集中在前端，不需要补后端服务
- 与“项目内置测试视频”场景贴合
- 可快速验证 Kimi 视频理解与景区补全效果

该方案的已知代价：
- API Key 会出现在前端运行环境中，不适合正式上线
- 大视频会带来较高 token 消耗、较慢请求速度和较高失败概率
- 需要在前端显式处理文件体积与模型返回格式问题

## 4. 用户与入口定义

### 4.1 demo 入口定义
当前 demo 不是“用户上传视频”，而是“项目默认读取测试视频并发起分析”。

页面入口策略：
- 默认显示项目内置测试视频
- 显示视频文件名与可选的文件大小信息
- 提供“开始分析”按钮
- 提供“替换视频（仅调试）”按钮

语义要求：
- 页面不把“替换视频”表述成正式产品能力
- 页面上的替换行为仅服务开发调试与演示

### 4.2 目标行为
用户（或演示者）打开页面后：
1. 页面展示当前测试视频
2. 点击“开始分析”
3. 前端完成视频预检查
4. 发起第一阶段视频理解
5. 发起第二阶段景区补全
6. 渲染最终景点速查卡

## 5. 两阶段调用架构

### 5.1 阶段一：视频理解
目标：
- 只根据视频内容提取景点结构化结果
- 不联网补充，不主动扩写超出视频的信息

输入：
- 整段本地视频，转成 `data:video/...;base64,...`
- 固定的系统提示词与输出结构约束

模型：
- `kimi-k2.6`

输出：
- 中间结构化 JSON，建议命名为 `Stage1SpotExtraction`

第一阶段应重点产出：
- 主景点名称
- 城市或区域
- 视频中可识别的亮点
- 打卡点
- 特色小吃
- 文创候选
- 周边候选
- 出行与住宿提示候选
- 置信度或可靠性标记

原则：
- 未在视频中出现的信息不要编造
- 不确定时可返回空数组或较保守文案

### 5.2 阶段二：景区补全
目标：
- 基于第一阶段提取结果，对景区做联网补充
- 优先补强景点亮点、打卡点解释、小吃/文创理由、周边顺路推荐
- 出行方式和住宿仍仅作为辅助信息

输入：
- 第一阶段的结构化 JSON
- Kimi 内置 `$web_search`
- 固定的系统提示词与最终输出结构约束

模型约束：
- 仍用 Kimi
- 必须关闭 thinking
- 允许使用 `builtin_function.$web_search`

输出：
- 最终 `SpotGuide`

原则：
- 搜索补充优先服务于“景点本身”
- 如果搜索结果不足，保留第一阶段信息而不是过度脑补
- 不把出行方式和住宿抬升为核心内容

## 6. JSON 模板文件设计
本次设计使用 JSON 模板文件组织请求体，而不是把 prompt 和输出约束散落在代码中。

建议新增两个模板文件：
- `src/prompts/kimi-video-analysis.template.json`
- `src/prompts/kimi-spot-enrichment.template.json`

### 6.1 视频理解模板
文件：`src/prompts/kimi-video-analysis.template.json`

职责：
- 描述第一阶段请求的模型、温度、系统提示词和输出结构要求
- 明确“只基于视频内容提取信息”

建议字段：
- `model`
- `temperature`
- `response_format`
- `system_prompt`
- `user_prompt_template`
- `output_schema`
- `constraints`

第一阶段输出建议结构：

```json
{
  "coreSpotName": "string",
  "city": "string",
  "summary": "string",
  "highlights": ["string"],
  "checkpoints": ["string"],
  "foods": ["string"],
  "souvenirs": ["string"],
  "nearbyCandidates": ["string"],
  "transportHints": ["string"],
  "stayHints": ["string"],
  "tips": ["string"],
  "confidence": "high | medium | low"
}
```

### 6.2 景区补全模板
文件：`src/prompts/kimi-spot-enrichment.template.json`

职责：
- 描述第二阶段请求的模型、工具、系统提示词和最终输出结构要求
- 明确使用 `$web_search`
- 明确输出要严格对齐前端 `SpotGuide`

建议字段：
- `model`
- `thinking`
- `tools`
- `response_format`
- `system_prompt`
- `user_prompt_template`
- `output_schema`
- `constraints`

最终输出必须映射到：

```ts
type SpotGuide = {
  source: {
    rawInput: string
    kind: "url" | "text"
  }
  coreSpot: {
    title: string
    city?: string
    summary: string
    bestTime?: string
    audienceTags: string[]
  }
  highlights: Array<{
    title: string
    description: string
  }>
  checkpoints: Array<{
    name: string
    description: string
    photoTip?: string
    stayHint?: string
  }>
  foodAndSouvenirs: Array<{
    name: string
    category: "food" | "souvenir"
    reason: string
  }>
  nearbyRecommendations: Array<{
    name: string
    reason: string
    relationHint?: string
  }>
  extraInfo: {
    transportTags: string[]
    stayTags: string[]
    durationHint?: string
    tips: string[]
  }
}
```

## 7. 前端调用链路

### 7.1 页面输入层
页面新增一个“测试视频面板”，显示：
- 当前测试视频文件名
- 文件大小
- “开始分析”按钮
- “替换视频（仅调试）”按钮

其中：
- 默认视频来自项目内置测试文件
- 替换视频仅用于调试，不作为正式产品主入口

### 7.2 文件预检查
在真正调用 Kimi 之前，前端必须先做预检查：
- 文件类型是否属于支持的视频格式
- 文件是否存在
- 文件大小是否超出 demo 建议范围

若文件过大：
- 阻止继续分析
- 向用户提示“当前 demo 不建议处理该视频，请换一个更小的视频”

这一点是本次方案偏向 “A + C，且偏 C” 的关键实现要求。

### 7.3 读取视频
浏览器通过 `FileReader` 读取视频文件内容，转换成 base64。

输出形式：
- `data:video/mp4;base64,...`

该结果作为第一阶段请求中的视频输入内容。

### 7.4 第一阶段调用
前端执行：
1. 读取 `kimi-video-analysis.template.json`
2. 用实际视频 data URL 替换模板中的占位部分
3. 调用 Kimi `chat/completions`
4. 获取第一阶段结构化 JSON

该阶段产出中间结果，不直接给 UI 使用。

### 7.5 第二阶段调用
前端执行：
1. 读取 `kimi-spot-enrichment.template.json`
2. 将第一阶段 JSON 作为用户消息输入
3. 注册 Kimi 内置工具 `$web_search`
4. 关闭 thinking
5. 调用 Kimi
6. 获取最终 `SpotGuide`

### 7.6 渲染与降级
若第二阶段成功：
- 直接渲染最终 `SpotGuide`

若第二阶段失败但第一阶段成功：
- 把第一阶段结果映射为一个基础版 `SpotGuide`
- 页面提示：“联网补充失败，当前展示的是视频提取结果”

若第一阶段失败：
- 进入错误态
- 不渲染景点结果

## 10. 错误处理
本次必须覆盖以下错误情况：

### 10.1 视频相关错误
- 默认测试视频不存在
- 文件读取失败
- 文件类型不支持
- 文件过大

### 10.2 模型调用错误
- API Key 缺失
- Kimi 接口请求失败
- 第一阶段返回非 JSON
- 第二阶段返回非 JSON
- 第二阶段搜索工具失败

### 10.3 降级策略
- 第一阶段失败：直接报错
- 第一阶段成功、第二阶段失败：降级为基础结果
- 第二阶段部分字段缺失：保留第一阶段字段，不清空整个结果

- 两阶段 JSON 模板请求

本次不包含：

- 后端代理

- 多视频批处理

- 真实账号权限与配额管理

## 13. 风险与注意事项
- 视频体积过大时，浏览器读取和 base64 转换会变慢
- 直接把视频转为 data URL 可能带来较大的请求体
- 模型对视频的提取结果可能不稳定，因此必须用 JSON 结构强约束输出
- 第二阶段联网补充需要额外 token 成本
- 该方案是 demo 优先方案，不适合作为生产架构

## 14. 推荐实施顺序

4. 新增第一阶段结果映射为 `SpotGuide` 的转换层
5. 扩展 store 状态流转
6. 页面接入“开始分析 / 替换视频（仅调试）”
7. 增加降级与错误提示
8. 补齐测试与联调

## 15. 结论
本次设计是在现有“景点速查页”基础上，为 demo 新增一条真实 AI 视频处理链路。它不是面向最终用户的上传产品，而是面向当前项目测试视频的内部演示流程。

该方案的核心价值是：
- 用项目内视频替代 mock 文本输入
- 用 Kimi 视频理解替代手写解析器
- 用 Kimi `$web_search` 补充景区信息
- 最终仍然回到统一的 `SpotGuide` 渲染结构

这样既能快速验证“视频 -> 景点速查卡”的可行性，也能最大限度复用当前已经完成的前端结果页。

# 文本输入分析设计

## 背景

当前首页的 `抖音链接 / 口令 / 文本` 输入区已经可以点击 `一键解析`，但文本链路实际仍走 `mockParserAdapter`。它主要依赖固定标签格式，例如 `主景点`、`亮点`、`打卡点`、`小吃`、`文创` 等字段拆行，因此更接近演示用 mock，而不是面向真实用户的文本分析能力。

用户当前目标是先把“纯文本分析”做可用，暂时不要求抖音链接或口令可用。文本场景需要同时支持：

- 输入单个景点名或少量关键词，例如 `雁荡山`、`雁荡山 门票 住宿 美食`
- 输入一整段攻略文本，由系统提炼关键词并生成结果卡片
- 如果输入的是抖音链接或口令，第一版直接拦截并提示当前只支持文本

## 目标

- 让文本入口对“关键词型输入”和“攻略段落型输入”都可用
- 复用现有 `SpotGuide` 结果页、Kimi 补全与稀疏栏目二次补全能力
- 第一版明确不支持真实抖音链接 / 口令解析，并给出清晰提示
- 在 Kimi 失败时保留本地基础结果，避免页面空白

## 非目标

- 不实现真实抖音链接解析
- 不实现抖音口令识别后的还原或抓取
- 不重做结果页 UI
- 不替换当前视频分析链路

## 方案对比

### 方案 A：继续增强 `mockParserAdapter`

优点：

- 改动最小
- 不需要新增服务层

缺点：

- `mockParserAdapter` 语义已经偏 demo/mock，继续承载正式文本分析会让职责越来越乱
- 很难自然支持“关键词查询 -> 联网补全”这类真实能力

### 方案 B：所有文本直接交给 Kimi

优点：

- 结果质量理论上最好
- 关键词和长文本都能统一处理

缺点：

- 失败兜底较弱
- 无法在 Kimi 失败时稳定给出基础结构化结果
- 输入分类与错误提示会混在一起，不利于后续扩展

### 方案 C：混合路由，推荐

做法：

- 先对输入做分类：`url_or_token`、`keyword_query`、`travel_note_text`
- `keyword_query`：提取景点名与意图词后，生成轻量 stage1，再走 Kimi 补全
- `travel_note_text`：先做本地关键词提炼，再走 Kimi 整理和联网补齐
- `url_or_token`：第一版直接拦截

优点：

- 同时覆盖短关键词与长文本
- 能复用现有 Kimi 补全链路
- Kimi 失败时仍可保留本地提炼结果

缺点：

- 比纯规则方案多一层输入分类与文本预处理

推荐采用方案 C。

## 设计

### 1. 输入分类

新增一个文本输入分类模块，建议放在 `src/services/textGuideAnalyzer.ts` 或相邻工具文件中。

输入分类结果分为三类：

- `url_or_token`
  - 命中 `http(s)://`
  - 命中明显抖音分享文案或口令特征
- `keyword_query`
  - 文本较短
  - 主要由景点名、城市名、意图词组成
  - 例如 `雁荡山`、`雁荡山 门票 住宿 美食`
- `travel_note_text`
  - 文本较长
  - 含多句攻略描述、推荐语、行程说明

分类规则不追求 NLP 级准确率，只要求第一版稳定区分“链接/口令”和“纯文本”，以及“短关键词”和“长文本”。

### 2. 文本分析总入口

新增一个正式的文本分析服务，例如：

```ts
analyzeTextGuide(inputText: string): Promise<{
  guide: SpotGuide
  partialMessage: string | null
}>
```

`useRideGuideStore.parseNow()` 不再直接依赖 `mockParserAdapter.parse()`，而是改为调用这个正式服务。

处理逻辑：

- 空输入：保持现有 `INVALID_INPUT`
- `url_or_token`：直接抛出明确错误
- `keyword_query`：走关键词路由
- `travel_note_text`：走攻略文本路由

### 3. 关键词型输入路由

对于短关键词输入，先提取：

- 主景点候选名
- 城市词
- 意图词，如 `门票`、`交通`、`住宿`、`美食`、`路线`

然后构造一个轻量 `Stage1SpotExtraction`：

- `coreSpotName` 使用主景点候选
- `highlights`、`checkpoints`、`foods`、`nearbyCandidates` 初始可为空
- `transportHints`、`stayHints`、`tips` 可根据意图词生成少量引导线索

再直接调用现有：

- `enrichSpotWithKimi(stage1)`
- 稀疏栏目二次补全逻辑沿用 `useRideGuideStore` 当前实现

如果 Kimi 失败，则回退为一个基础 guide：

- 标题来自景点关键词
- 摘要说明为“根据文本关键词生成的基础结果”
- 结果页仍然可展示

### 4. 攻略段落型输入路由

对长文本先做本地轻量提炼，产出文本版 stage1：

- 主景点名：优先识别景区/地名高频词
- 城市：从已知城市词或上下文中提取
- 亮点词：提取高频景观、玩法、氛围词
- 打卡点：提取景点名、区块名、景区子点
- 美食/文创：提取典型食物名、伴手礼词
- 交通/住宿/贴士：从句子中抽线索

这一阶段只做“尽量提炼”，不追求完美结构化。

提炼结果再进入 `enrichSpotWithKimi()`，由 Kimi 负责：

- 统一生成 `SpotGuide`
- 联网补全缺失栏目
- 输出更自然的景点摘要和推荐理由

如果 Kimi 失败，则展示本地提炼版结果，并通过 `partialMessage` 告知“当前展示的是文本提炼结果”。

### 5. 链接 / 口令拦截

当输入识别为 `url_or_token` 时，第一版直接返回：

- 错误码仍可使用 `INVALID_INPUT`
- 错误文案改为：
  - `当前版本仅支持纯文本分析，请粘贴景点名、关键词或一段攻略文字`

这样既符合当前能力边界，也避免用户误以为抖音链接已经打通。

### 6. 与现有状态流的衔接

`parseNow()` 仍然保留现有文本分析状态：

- 点击 `一键解析` 后进入 `loading`
- 成功后进入 `success`
- 如果 Kimi 失败但本地提炼成功，可进入 `partial_success` 或保留 `success + partialMessage`

推荐做法：

- 文本链路也支持 `partialMessage`
- 这样与视频链路的“联网失败但保底展示”体验一致

### 7. UI 文案

第一版保持首页标题不变，但建议微调输入区提示文案：

- 当前：`粘贴一段内容即可开始，支持纯文本攻略。`
- 建议：`当前版本支持景点名、关键词和攻略文字；抖音链接 / 口令暂未开放。`

这样能提前降低误解。

## 实现拆分

### 模块建议

- `src/services/textGuideAnalyzer.ts`
  - 文本入口总调度
- `src/utils/textInputClassifier.ts`
  - 输入分类
- `src/utils/textStage1Extractor.ts`
  - 长文本本地提炼 stage1
- `src/utils/textKeywordQuery.ts`
  - 短关键词提取主景点与意图词

### 现有文件改动

- `src/store/useRideGuideStore.ts`
  - `parseNow()` 改为调用正式文本分析服务
- `src/components/InputPanel.tsx`
  - 调整辅助文案
- `src/utils/mockParserAdapter.ts`
  - 保留用于 demo/mock，不再作为正式文本入口主实现

## 错误处理

- 空输入：提示用户先输入内容
- 链接/口令：提示当前只支持文本
- 文本过短且无法识别景点：提示用户补充 2-5 个关键词
- Kimi 失败：展示本地提炼结果并提示“联网补充失败，当前展示基础结果”

## 测试

至少补以下测试：

- `雁荡山` 这类单景点关键词输入
- `雁荡山 门票 住宿 美食` 这类组合关键词输入
- 一整段攻略文字输入
- 抖音链接输入被拦截
- 抖音口令输入被拦截
- Kimi 失败时回退本地提炼结果
- 长文本提炼结果仍可走现有稀疏栏目补全逻辑

## 风险与取舍

- 第一版输入分类采用规则法，可能存在少量误判
- 长文本本地提炼不追求高召回，重点是给 Kimi 一个更稳定的起点
- 由于抖音链接/口令被明确拦截，短期内会和输入区标题存在轻微不一致，但可以通过提示文案缓解

## 验收标准

- 用户输入单个景点名可生成可展示的结果卡片
- 用户输入关键词组合可生成更偏向对应需求的结果
- 用户输入攻略段落可产出结构化景点速查结果
- 用户输入抖音链接或口令时不会误走解析成功，而是得到明确提示
- 结果页继续复用现有卡片结构，不新增白屏或运行时错误

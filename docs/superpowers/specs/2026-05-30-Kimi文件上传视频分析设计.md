# 2026-05-30 Kimi 文件上传视频分析设计

## 背景

当前项目为了解决 `chat/completions` 请求体 `4MB` 限制，采用了“前端本地抽帧 -> 发图片给 Kimi”方案。但从实际结果看，这个方案存在明显缺陷：

- 很难稳定命中景区牌匾、字幕、路牌、山门等关键地点线索
- 最终结果经常只能得到“待确认景点”
- 页面即使分析完成，也可能缺少景区名称和周边特色

根因是：当前需求本质上更适合“完整视频理解”，而不是“前端自行猜关键帧后再识别”。

结合用户提供的文档与 Kimi 能力说明，更合适的方案是：

1. 通过 `/v1/files` 上传视频文件
2. 获取 `file_id`
3. 在 `chat/completions` 中通过 `file_id` 引用视频
4. 让 Kimi 直接基于完整视频做识别与分析

## 目标

- 用 `Kimi /v1/files` 替换当前前端本地抽帧主方案
- 让 Kimi 直接处理完整视频，而不是只看若干本地抽帧图片
- 避免 `4MB` 限制问题
- 提高景区名称、关键地点、景点亮点和周边特色的识别质量
- 保留现有第二阶段联网补全和结果展示链路

## 非目标

- 不继续增强当前“关键地点导向抽帧”作为主方案
- 不做视频存储服务或长期文件管理系统
- 不引入复杂账户体系或任务队列系统
- 不改变产品主页面结构

## 架构变化

### 当前架构

- 前端直接读取本地视频
- 前端本地抽帧
- 前端将代表帧图片发给 Kimi

### 新架构

- 前端将本地视频交给后端
- 后端调用 Kimi `/v1/files` 上传视频
- 后端拿到 `file_id`
- 后端调用 `chat/completions`，通过 `file_id` 引用视频
- 后端返回第一阶段结构化结果给前端
- 前端继续使用现有第二阶段补全和展示逻辑，或同样由后端统一完成

## 为什么必须引入后端

虽然当前 Demo 曾允许前端直连 Kimi，但文件上传链路不再适合纯前端直连：

- 上传文件更适合服务端处理
- 避免将长期有效的 API Key 暴露在浏览器
- 文件上传、`file_id`、请求重试、错误记录都更适合后端处理
- 后续如果要从本地视频切换到“抖音链接解析后拿 MP4 URL”，后端更容易扩展

因此，新方案应明确以“前端 + 轻量后端代理”作为主架构。

## 核心链路

### 第一步：前端提交视频

前端不再本地抽帧，而是直接将视频文件提交给后端接口，例如：

- `POST /api/video/analyze`

请求体可以是：

- `multipart/form-data`
- 包含 `video` 文件字段

### 第二步：后端上传文件到 Kimi

后端调用：

- `POST https://api.moonshot.cn/v1/files`

上传成功后拿到：

- `file_id`

### 第三步：后端引用 `file_id` 调用视频分析

后端调用：

- `POST https://api.moonshot.cn/v1/chat/completions`

请求中引用：

- `file_id`

由 Kimi 直接对完整视频做理解和结构化提取。

### 第四步：生成第一阶段结构化结果

第一阶段仍输出与当前兼容的结构：

- `coreSpotName`
- `city`
- `summary`
- `highlights`
- `checkpoints`
- `foods`
- `souvenirs`
- `nearbyCandidates`
- `transportHints`
- `stayHints`
- `tips`
- `confidence`

### 第五步：补全与展示

后续策略有两种可选方式：

- 方式 A：后端只返回第一阶段结果，前端保留现有第二阶段补全
- 方式 B：后端统一执行第一阶段 + 第二阶段，再一次性返回可展示结果

当前阶段推荐先采用方式 A，以减少改动面。

## 推荐实现范围

### 第一阶段迁移到后端

优先将第一阶段迁移到后端：

- 前端去掉本地抽帧主流程
- 后端负责上传视频和调用 Kimi 视频理解
- 返回结构化 `Stage1SpotExtraction`

### 第二阶段暂时保留现状

第二阶段暂时仍可保留现有前端补全逻辑：

- 这样能最小化迁移成本
- 先验证完整视频理解是否显著提升识别质量

## 前端改动

### `useRideGuideStore`

调整视频分析流程：

- 仍保留视频校验
- 不再执行本地抽帧
- 改为直接调用后端视频分析接口
- 接收后端返回的 `Stage1SpotExtraction`
- 后续逻辑尽量复用现有补全、推断和展示链路

### `videoKeyframes`

当前抽帧工具不再作为主流程依赖：

- 可以保留一段时间作为历史兜底
- 但不再是默认分析路径

## 后端改动

建议新增一个轻量后端目录，例如：

- `api`
- 或 `server`

后端至少需要：

- 一个视频上传分析接口
- 一个 Kimi files client
- 一个 Kimi chat client
- 请求体和错误转换逻辑

## 错误处理

### 文件上传失败

明确透传以下错误：

- 文件格式不支持
- 文件过大
- Kimi `/v1/files` 返回 4xx/5xx

### 视频分析失败

- 继续透传 Kimi 真实错误
- 不吞掉服务端报错

### 前端展示失败

- 仍保留现有结果归一化与空态显示
- 不允许因后端返回不完整数据而白屏

## 状态流

现有主状态可以尽量保留：

- `validating_video`
- `reading_video`
- `analyzing_video`
- `enriching_spot`
- `success`
- `partial_success`
- `error`

其中：

- `reading_video` 不再表示“本地转 base64/抽帧”
- 而是表示“准备并上传视频到后端”

## 安全与部署

### Demo 阶段

即使是 Demo，也推荐至少做到：

- 前端不直接持有 Kimi 文件上传 Key
- 由后端代理调用 Kimi

### 部署建议

适合放在：

- Vercel Functions
- Render
- 阿里云函数

## 成功标准

- 本地视频分析不再依赖本地抽帧主链路
- 视频大小不再受 `chat/completions` 4MB 请求体限制影响
- Kimi 能基于完整视频输出更稳定的景区名称和关键地点信息
- 前端能正常展示第一阶段和后续补全结果
- 测试、类型检查和构建通过

## 风险与取舍

- 需要引入后端，复杂度高于当前纯前端方案
- 文件上传链路会增加网络等待时间
- 若后端未部署，前端本地联调方式需要调整
- 但从识别质量角度，这是比继续优化本地抽帧更合理的主方案

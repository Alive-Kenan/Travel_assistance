# 视频长耗时提示设计

## 背景

当前 demo 已接入 Kimi 两阶段视频解析链路，真实联调时可以成功发起视频请求和 Kimi 接口请求。但默认测试视频体积较大，视频分析阶段可能持续较长时间，页面会长时间停留在“分析中…”，容易让用户误以为页面卡死或请求失败。

本次设计只解决“等待过程中的用户感知”问题，不改变 Kimi 请求协议，不新增后端，不自动中断正在进行的请求。

## 目标

- 在视频分析耗时较长时，明确告诉用户当前仍在处理中
- 让用户区分“正常处理中”和“耗时较长但未失败”
- 不自动报错，不自动取消，不影响当前成功/降级/失败逻辑
- 保持 demo 方案简单可运行

## 非目标

- 不实现真实上传进度条
- 不伪造百分比进度
- 不新增后端轮询或任务系统
- 不改动文本解析链路

## 方案概述

采用“阶段提示 + 长耗时升级文案”方案。

页面仍然沿用当前视频状态流：

- `validating_video`
- `reading_video`
- `analyzing_video`
- `enriching_spot`
- `success`
- `partial_success`
- `error`

其中仅在 `analyzing_video` 阶段增加“等待时长感知”。

## 数据设计

在 store 中新增轻量等待信息，供 UI 判断是否进入长耗时提示：

- `videoAnalyzeStartedAt: number | null`
- `videoAnalyzeWaitLevel: "normal" | "slow" | "very_slow"`

状态切换规则：

- 进入 `analyzing_video` 时记录开始时间，并初始化为 `normal`
- 当等待超过第一阈值时，升级为 `slow`
- 当等待超过第二阈值时，升级为 `very_slow`
- 一旦视频链路进入 `success`、`partial_success`、`error`、`idle`，清空等待信息

## 文案设计

基础阶段文案保持不变：

- `validating_video`：正在检查测试视频…
- `reading_video`：正在读取视频…
- `analyzing_video`：正在分析视频…
- `enriching_spot`：正在补充景区信息…

长耗时升级文案：

- `slow`：视频较大，分析可能需要 1-3 分钟，请耐心等待…
- `very_slow`：当前仍在分析中；如果长时间无结果，可稍后重试或替换更短测试视频。

展示规则：

- `normal` 时继续显示原始阶段提示
- `slow` 和 `very_slow` 时，替换 `analyzing_video` 的默认文案
- `partial_success` 仍沿用当前橙色降级提示，不受本设计影响

## 阈值设计

为了兼顾 demo 体验和大视频现实耗时，采用固定阈值：

- 第一阈值：15 秒，进入 `slow`
- 第二阈值：45 秒，进入 `very_slow`

阈值写为可复用常量，便于后续调整。

## 组件改动

### `useRideGuideStore.ts`

- 在视频分析开始时启动等待级别更新逻辑
- 在视频链路结束或重置时清理计时器和等待状态
- 不改变现有成功、降级、失败分支

### `StatusBanner.tsx`

- 接收 `videoAnalyzeWaitLevel`
- 当 `status === "analyzing_video"` 时，根据等待级别切换展示文案
- 保持现有样式体系，只微调文案，不引入新的复杂 UI

### `Home.tsx`

- 将新的等待级别从 store 传给 `StatusBanner`
- 不改现有按钮、弹窗和结果面板逻辑

## 失败与边界

- 如果请求很快成功，用户只会看到普通阶段提示
- 如果请求很慢但最终成功，用户会先看到长耗时提示，再进入成功结果
- 如果请求很慢后失败，仍进入现有错误弹窗
- 如果第二阶段补全失败，仍进入现有 `partial_success`

## 测试策略

新增针对长耗时提示的轻量测试：

- 初始 `analyzing_video` 时显示普通分析文案
- 等待级别为 `slow` 时显示“1-3 分钟”提示
- 等待级别为 `very_slow` 时显示“可稍后重试或替换更短测试视频”提示

必要时补一个 store 测试，验证视频分析开始与结束时等待状态会正确初始化和清空。

## 风险

- 当前没有真实服务端进度，只能基于时间提示“可能较慢”，不能保证准确反映后台处理进度
- 长视频若持续占用很长时间，页面仍然会停在处理中；本次只优化认知，不解决根因
- 如果后续改成后端代理或异步任务制，需要重新设计进度提示策略

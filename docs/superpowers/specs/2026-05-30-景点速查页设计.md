# 景点速查页设计文档

## 1. 背景与目标
当前项目已经有一个可运行的单页 H5 原型，但整体叙事仍然偏向“骑行攻略解析”。产品方向现已明确调整为“以景点本身为中心的旅行信息速查工具”，核心价值不再是某一种出行方式，而是把短视频中的景点信息提炼为可理解、可决策、可执行的旅行卡片。

本次设计的目标是：
- 保留现有页面的“粘贴链接 -> 一键解析 -> 结果卡片展示”主链路
- 将结果内容从骑行字段重构为景点字段
- 让页面强调“景点为什么值得去、到了以后看什么、吃什么、买什么、周边还能顺路逛什么”
- 将出行方式与住宿降级为补充信息，为后续迭代预留位置

## 2. 产品定位
- 产品核心：景点速查工具，而不是骑行工具
- 用户动作：先粘贴短视频链接或文本，再查看结构化结果
- 用户关注点：景点亮点、打卡点、特色小吃、文创、周边顺路推荐
- 补充信息：出行方式、住宿建议、游玩提醒，仅作为结果页底部辅助模块

一句话定位：
> 把短视频里的景点内容，整理成一屏看懂的轻旅行速查指南。

## 3. 设计原则
- 景点优先：所有信息排序都围绕“景点本身是否值得去”展开
- 主次分明：核心内容突出，补充信息弱化
- 保持工具感：首屏仍然只有一个动作，不引入复杂筛选
- 模块清晰：结果页按用户阅读路径分块，减少信息堆叠
- 平滑迁移：尽量复用现有输入、状态、加载、错误处理与基础样式

## 4. 方案结论
采用 `景点主卡 + 周边延展` 方案。

该方案的核心结构是：
- 先展示一个主景点，明确这个地方的价值与吸引力
- 再展开景点内部或核心区域的亮点与打卡点
- 接着补充小吃、文创等更具旅行消费感的内容
- 最后延展到周边顺路推荐和补充信息

选择该方案的原因：
- 最符合“景点本身是主角”的产品定位
- 比纯标签切换式方案更容易形成第一眼吸引力
- 比内容流专题方案更保留工具产品的效率感

## 5. 页面结构

### 5.1 首页主链路
首页不增加前置筛选，仍然只保留一个主要动作：
1. 用户粘贴抖音链接、口令或文本
2. 点击“一键解析”
3. 页面进入加载态
4. 成功后渲染景点速查结果
5. 失败时显示错误弹窗并允许重试

### 5.2 结果页信息结构
结果页采用以下固定阅读顺序：

1. 景点主卡
2. 景点亮点
3. 必打卡点
4. 特色小吃 / 文创
5. 周边顺路推荐
6. 补充信息

这样设计的目的是让用户先判断“值不值得去”，再逐步了解“到了以后重点看什么、吃什么、买什么、顺路还能去哪”，最后再查看交通和住宿等辅助信息。

## 6. 各模块定义

### 6.1 景点主卡
作用：建立第一印象，快速回答“这是什么地方，为什么值得去”。

展示内容：
- 景点名称
- 所在城市/区域
- 一句话亮点总结
- 推荐游玩时段或季节
- 适合人群标签，例如“拍照党”“亲子”“周末短途”

设计要求：
- 作为结果页视觉权重最高的模块
- 标题与一句话摘要必须在首屏内可见
- 不展示骑行类数字指标

### 6.2 景点亮点
作用：解释景点受欢迎的原因。

展示内容：
- 3 到 5 条景点核心吸引点
- 每条亮点用短句说明，例如自然景观、历史氛围、夜景、互动体验、季节限定

设计要求：
- 使用简洁的高亮卡片或强调条目
- 每条亮点说明不超过两行，避免内容冗长

### 6.3 必打卡点
作用：把视频里的碎片镜头整理成用户可执行的停留点位。

展示内容：
- 打卡点名称
- 推荐理由
- 适合拍什么或体验什么
- 可选字段：建议停留时间

设计要求：
- 支持列表式连续浏览
- 每个点位都要有明确的“为什么值得停留”

### 6.4 特色小吃 / 文创
作用：体现旅行体验的“吃”和“买”，增强景点的消费与记忆价值。

展示内容：
- 特色小吃名称与简短说明
- 推荐文创或纪念品名称与卖点
- 可选字段：适合买来送人、适合打包带走、适合作为地标纪念

设计要求：
- 小吃与文创可放在同一模块中，以标签或分组区分
- 内容以“推荐理由”优先，而不是纯名称堆叠

### 6.5 周边顺路推荐
作用：把单景点扩展成半日游或一日游链路。

展示内容：
- 周边可顺路去的小景点、街区、小吃街、文创店
- 与主景点的关系说明，例如“顺路可逛”“步行可达”“适合一起安排”
- 可选字段：推荐组合方式

设计要求：
- 该模块是延展内容，重要性低于主景点内容但高于补充信息
- 语义上要强调“顺路”和“搭配游玩”

### 6.6 补充信息
作用：提供辅助决策信息，但不抢景点本身的视觉权重。

展示内容：
- 出行方式建议
- 住宿建议
- 建议停留时长
- 避坑提醒或注意事项

设计要求：
- 放在结果页靠后位置
- 使用次级标题、较轻背景或较弱强调样式
- 当前阶段只保留基础展示，后续再扩展深度

## 7. 交互设计

### 7.1 输入与解析
- 用户仍然先粘贴内容，不新增首页筛选项
- 点击解析后进入加载态，显示骨架屏
- 加载完成后自动聚焦结果区

### 7.2 结果出现节奏
结果模块按层级逐步出现：
- 第一层：景点主卡 + 景点亮点
- 第二层：必打卡点 + 特色小吃 / 文创
- 第三层：周边顺路推荐 + 补充信息

这样能强化景点优先的阅读顺序，减少用户第一眼被次要信息打断。

### 7.3 错误与降级
- 输入为空：提示用户输入链接或文本
- 解析失败：给出重试入口
- 内容信息不足：结果中允许出现部分模块缺省，但景点主卡必须尽量保留

### 7.4 后续可扩展交互
本期仅保留结构化展示，不引入复杂切换。后续可以扩展：
- 展开更多
- 一键复制景点清单
- 收藏或导出结果卡片
- 交通/住宿深度展开

## 8. 视觉方向
- 延续现有青绿色主调、暖橙点缀和浅灰白背景
- 从“骑行工具感”调整为“景点旅行速查感”
- 图标语义从路线、装备、骑行指标，转向景点、相机、美食、文创、位置与推荐
- 结果页视觉重心从数字统计卡，改为主卡摘要与内容模块

文案语气调整方向：
- 从“路线执行型”变为“景点探索型”
- 推荐文案使用“值得看”“值得停留”“顺路可逛”“适合买”“适合拍照”等表达

## 9. 数据结构调整
当前结果结构偏骑行，需要改为景点导向的数据模型。

建议的数据结构如下：

```ts
export type SpotGuide = {
  source: {
    rawInput: string
    kind: "url" | "text"
  }
  coreSpot: {
    title: string
    city?: string
    summary: string
    bestTime?: string
    audienceTags: string[]
  }
  highlights: Array<{
    title: string
    description: string
  }>
  checkpoints: Array<{
    name: string
    description: string
    photoTip?: string
    stayHint?: string
  }>
  foodAndSouvenirs: Array<{
    name: string
    category: "food" | "souvenir"
    reason: string
  }>
  nearbyRecommendations: Array<{
    name: string
    reason: string
    relationHint?: string
  }>
  extraInfo: {
    transportTags: string[]
    stayTags: string[]
    durationHint?: string
    tips: string[]
  }
}
```

约束说明：
- `coreSpot` 必须存在
- `highlights`、`checkpoints` 至少有一个非空
- `extraInfo` 中各字段可为空，但对象结构保留

## 10. 解析策略
本期仍使用纯前端 mock 解析适配器，但解析重点改为：
- 景点名称
- 景点亮点
- 打卡点
- 小吃 / 文创
- 周边顺路推荐
- 补充信息

不再把以下字段作为核心结果：
- 里程
- 爬升
- 装备列表
- 骑行路线

解析策略应遵循：
- 优先保证主景点名称与摘要完整
- 如果信息不足，可减少周边或补充模块内容
- 缺失信息用轻量兜底文案，而不是让主界面空白

## 11. 组件改造范围
优先复用现有项目结构，只替换与“骑行语义”强绑定的部分。

建议改造如下：
- 保留：输入区、加载态、错误弹窗、按钮、标签、基础布局
- 替换：`RideGuideCards` 为新的景点结果组件，例如 `SpotGuideCards`
- 调整：`Hero` 文案、`Footer` 文案、结果区空态文案
- 更新：类型定义、mock 解析器、zustand 中的结果类型

组件职责建议：
- `Hero`：品牌与一句话定位
- `InputPanel`：输入与触发解析
- `ResultPanel`：根据状态切换空态、加载态、结果态
- `SpotGuideCards`：承载景点结果模块
- `Dialog`：错误与提醒

## 12. 状态流
保留当前状态机：
- `idle`
- `loading`
- `success`
- `error`

保留当前行为：
- 输入内容
- 清空
- 使用示例
- 发起解析
- 取消解析
- 错误关闭与重试

仅更新：
- `result` 的类型
- 成功态渲染组件
- 示例数据内容

## 13. 测试要求
至少覆盖以下验证点：
- 空输入时返回输入错误
- 示例输入能够生成景点主卡
- 结果中能看到亮点、打卡点、小吃/文创、周边推荐
- 补充信息模块存在但位于结果后部

前端验证要点：
- 首屏主标题已从骑行语义改为景点语义
- 解析后优先出现景点主卡
- 不再展示里程、爬升、装备等骑行核心指标

## 14. 实施边界
本次改造只覆盖前端展示与 mock 数据结构，不包含：
- 真实抖音链接解析服务接入
- 地图能力
- 收藏与用户体系
- 交通/住宿深度推荐逻辑

这些能力作为后续迭代项保留。

## 15. 推荐实施顺序
1. 修改标题文案、品牌叙事与空态文案
2. 将结果类型从骑行结构改为景点结构
3. 重写 mock 解析器与示例数据
4. 替换结果卡片组件
5. 更新测试并重新验证页面

## 16. 结论
本次设计的核心是把现有“骑行攻略解析页”升级为“景点速查页”。

页面不会改成复杂的旅行平台，而是继续保持单页、轻量、快速解析的工具形态。区别在于，结果内容会从“怎么骑、带什么、风险是什么”，转为“这个景点为什么值得去、到了看什么、吃什么、买什么、周边还能怎么逛”。这使产品定位更贴近旅行场景，也为未来逐步补充出行方式和住宿信息留下了合理空间。

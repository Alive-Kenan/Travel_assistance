# 2026-05-30 Kimi 抽帧视频解析设计

## 背景

当前 Demo 的第一阶段将本地视频整体转为 `data:video/...;base64,...` 后直接放入 `chat/completions` 的 `messages` 中，请求体大小达到约 28MB，超过接口 `4MB` 限制，导致无法继续联调。

Kimi 模型具备多模态理解能力，但当前前端直连方案不适合传整段视频。为了在不改动整体产品结构的前提下尽快跑通 Demo，需要将“整段视频直传”改为“浏览器本地抽帧后发送代表帧”。

## 目标

- 保留当前两阶段流程：
  - 第一阶段：识别景点与基础信息
  - 第二阶段：联网补全景区信息
- 将第一阶段输入从整段视频改为少量代表帧图片
- 尽量提高景点识别准确性，降低“抽不到关键画面”的风险
- 保持现有长耗时提示、错误透传和第二阶段降级逻辑

## 非目标

- 不实现服务端视频上传链路
- 不接入 Kimi 文件上传接口
- 不做复杂的视频镜头切换检测或专业视频分析算法
- 不修改第二阶段景区补全模板和渲染结构

## 方案总览

采用“三层抽帧 + 一次补抽重试”的策略：

1. 第一层：按时间轴均匀采样 10 帧，采样区间为视频的 10% 到 90%
2. 第二层：在浏览器本地对采样结果进行质量筛选，剔除明显无效帧和重复帧
3. 第三层：选出 5 张代表帧发给 Kimi 做首轮识别
4. 若模型返回的结果置信度不是 `high`，或无法稳定识别核心景点，则再补抽 4 张新帧进行第二轮识别
5. 第二轮若仍无法得到可靠结果，则向用户返回明确失败信息，不输出编造内容

## 抽帧设计

### 抽帧区间

- 不从视频开头和结尾直接抽帧
- 默认采样区间为视频总时长的 10% 到 90%
- 目的是降低抽到片头 Logo、转场、黑屏、字幕页、片尾空镜的概率

### 第一轮采样

- 总采样数：10 帧
- 时间点：在 10% 到 90% 之间均匀分布
- 输出结果是原始候选帧列表，不直接全部发给模型

### 第二轮补抽

- 仅在第一轮结果不稳定时触发
- 补抽 4 帧
- 时间点优先选择第一轮相邻采样点之间的中间位置，尽量覆盖尚未充分观察到的片段
- 目标是提高命中关键地标、路牌、山门、牌匾、索道、夜景或字幕等识别线索的概率

## 本地质量筛选

为保证“抽帧准确性”不是单纯依赖运气，抽出的候选帧需要在浏览器本地做轻量筛选。

### 无效帧剔除

剔除以下明显低价值画面：

- 近乎纯黑或纯白的画面
- 清晰度过低的画面
- 视频尚未真正渲染完成导致的空白帧

### 重复帧剔除

- 对候选帧生成低成本的视觉摘要特征
- 如果相邻候选帧相似度过高，只保留信息量更高的一张
- 避免把连续几张几乎相同的风景重复发给模型，浪费请求体空间

### 代表帧选择

- 第一轮从通过筛选的候选帧中选出 5 张代表帧
- 优先保留：
  - 清晰度较高的帧
  - 时间位置分布更均匀的帧
  - 与其他帧重复度更低的帧

## 模型请求设计

### 第一阶段输入格式

第一阶段不再把视频作为文本注入 prompt，而是改为多模态消息：

- `system`：保留原有“只基于画面内容，不要编造”的约束
- `user.content`：改为数组，包含：
  - 任务说明文本
  - 5 张代表帧的 `image_url`

如果进入第二轮重试：

- 重新发起一次第一阶段请求
- 请求内容由：
  - 第一轮代表帧摘要说明
  - 第二轮补抽的 4 张新帧
  - 更明确的识别要求

### 请求体控制

- 所有帧都需要缩放到适合模型理解但不过大的分辨率
- 单帧优先压缩为 JPEG
- 最终请求体必须显著低于当前 4MB 限制，留出 prompt 和 JSON 包装余量

## 结果判定

第一轮完成后，如果满足以下任一条件，则视为结果不稳定，触发第二轮补抽：

- `confidence !== "high"`
- `coreSpotName` 缺失
- 返回内容为空或无法解析为预期 JSON

第二轮完成后：

- 若识别成功，继续进入第二阶段景区补全
- 若仍然失败，则结束第一阶段并返回明确错误

## 状态流设计

现有状态主流程保持不变：

- `validating_video`
- `reading_video`
- `analyzing_video`
- `enriching_spot`
- `success`
- `partial_success`
- `error`

内部实现上，`reading_video` 的职责从“读取整段视频 base64”调整为：

- 加载视频元数据
- 抽帧
- 压缩与筛选代表帧

`analyzing_video` 仍表示第一阶段调用 Kimi。现有长耗时提示逻辑继续使用，不需要调整状态定义。

## 错误处理

### 抽帧失败

出现以下情况时直接报错，不再请求 Kimi：

- 视频元数据读取失败
- 视频 seek 失败
- Canvas 导出图片失败
- 经过筛选后没有可用代表帧

错误提示应明确指向“视频抽帧失败”或“未提取到有效画面”，避免误判为鉴权或模型错误。

### 第一阶段失败

- 若 Kimi 返回 4xx/5xx，继续透传真实错误
- 若返回体不符合预期 JSON，提示“识别结果格式异常”
- 第二轮重试后仍失败，则进入 `error`

### 第二阶段失败

- 保持现有逻辑
- 第一阶段已有结构化结果时，第二阶段失败仍进入 `partial_success`

## 代码结构调整

### 新增能力

- 在 `src/utils` 增加视频抽帧工具
- 增加候选帧筛选与代表帧选择逻辑
- 增加第一阶段重试判定逻辑

### 调整能力

- `src/utils/promptTemplates.ts`
  - 第一阶段请求构造从“文本注入视频 data URL”改为“多模态图片数组”
- `src/services/kimiClient.ts`
  - 第一阶段输入参数从单个视频 data URL 改为代表帧数组
- `src/store/useRideGuideStore.ts`
  - 第一阶段前增加本地抽帧和筛选流程
  - 根据第一阶段结果决定是否补抽重试

## 测试策略

### 单元测试

- 抽帧请求构造测试
  - 不再出现 `data:video/...`
  - 正确注入多张 `image_url`
- 第一阶段重试判定测试
  - `confidence !== "high"` 时触发补抽
  - `coreSpotName` 缺失时触发补抽
- 错误处理测试
  - 抽帧失败时给出明确错误
  - 第二轮失败后进入 `error`

### 回归测试

- 保留并更新现有 `kimiClient` 测试
- 保留 store 中的：
  - 长耗时提示升级测试
  - 第二阶段失败降级为 `partial_success`
  - 真实错误透传

## 成功标准

- 默认测试视频不再触发 `total message size exceeds limit`
- 第一阶段请求体体积明显小于 4MB
- Demo 能够在第一阶段得到稳定结构化结果，必要时自动补抽一次
- 第二阶段补全逻辑与现有页面渲染保持兼容
- 测试、类型检查与构建通过

## 风险与取舍

- 抽帧策略可以显著提高命中率，但无法保证 100% 正确识别
- 如果原视频缺少清晰地标、牌匾、字幕或典型景观，模型仍可能只能给出中低置信度结果
- 当前方案优先保证 Demo 可运行和识别概率，而不是追求完整的视频理解能力
- 若后续仍需更高准确率，再考虑文件上传或更复杂的镜头切换检测
